# AGENTS.md: правила работы агента

Этот файл обязателен к прочтению перед началом любого модуля. Сам план модулей (M0-M19) лежит в `PLAN.md`. Исходное задание: `TZ-YouTube.md`.

Ты сеньёр Software engineer.

## 0. Правила работы

### 0.1 Git: только пользователь

- Агент НЕ выполняет никаких `git`-команд: ни `init`, `add`, `commit`, `branch`, `checkout`, `merge`, `rebase`, `push`, `pull`, `stash`, `reset`, ни чтения истории. Коммиты, ветки и историю ведёт пользователь.
- Агент не использует GitHub и любые внешние хостинги кода: нет CI в `.github/`, нет pre-commit-хуков, нет скриптов, которые вызывают `git`.
- Файл `.gitignore` агент может создать как обычный текстовый файл (без запуска git).
- В конце каждого модуля агент пишет отчёт: что сделано, список изменённых файлов, как проверить, результаты тестов. Если пользователь захочет, агент добавит одной строкой предложение текста для коммита, но сам ничего не фиксирует.
- В `.claude/settings.json` любые `git`-команды запрещены (см. M0 в `PLAN.md`), чтобы правило соблюдалось технически, а не только словами.
- Критерий проверки №8 из ТЗ (история коммитов) целиком на стороне пользователя. Рекомендация: коммитить после каждого закрытого модуля.
- Сборку итогового zip (каталог `.git`, диалоги `*.jsonl` из `~/.claude/projects/<проект>/`, обвязка) делает пользователь; агент готовит только чек-лист (M19 в `PLAN.md`).

### 0.2 Посильность для ИИ-агента

Это копия YouTube на уровне тестового задания, а не воспроизведение его внутренних алгоритмов. Принципы:

1. Только известные, хорошо документированные технологии: FastAPI, SQLAlchemy, Alembic, PostgreSQL, MinIO (S3 API через `boto3`), `ffmpeg`/`ffprobe`, nginx, Docker Compose, обычный HTML/CSS/JS.
2. Простое решение вместо масштабируемого: один видеофайл вместо лестницы качеств, обычный `<video>` вместо кастомного плеера, `ILIKE` + `pg_trgm` вместо поискового движка, сортировка по дате и просмотрам вместо рекомендаций.
3. Синхронный стек (SQLAlchemy sync + FastAPI-эндпоинты `def`): меньше подводных камней, чем в async, проще тесты и воркер.
4. Один модуль = один осмысленный объём работы, который агент способен целиком удержать в контексте и проверить. Модуль, который не помещается, делится на подмодули.
5. У каждой задачи проверяемый результат: запрос через Swagger/curl, тест `pytest` или экран в браузере.
6. Никаких внешних сервисов в рантайме (CDN, Google Fonts, внешние API): система должна работать на VM без доступа к интернету после сборки образов.
7. Если реализация выходит за рамки пунктов выше, агент останавливается и спрашивает пользователя, а не усложняет сам.

### 0.3 Что сознательно НЕ делаем

Рекомендательные алгоритмы и ранжирование ленты по поведению, адаптивный битрейт с несколькими качествами и HLS/DASH (только как опциональное расширение в конце), собственный видеоплеер, прямые трансляции, Shorts, монетизация и реклама, Content ID и автоматическая модерация, субтитры и автопереводы, уведомления и email-рассылки, история просмотров и «Смотреть позже», посты сообщества, ссылки-приглашения на приватные видео, CDN, шардирование, Kafka/Redis/Elasticsearch, Kubernetes, DRM, возобновляемая загрузка, мобильное приложение.

### 0.4 Сквозные правила

1. Вертикальный срез первым: сценарий «регистрация → загрузка → просмотр → лайк и комментарий» должен заработать после M8 (через API) и после M13 (через UI).
2. Каждый модуль закрывается чек-листом «Критерии готовности» и общим DoD (в конце `PLAN.md`). Пока он не выполнен, к следующему модулю не переходим.
3. Весь код пишет ИИ. Ключевые промпты сохраняются в `prompts/` (см. M0 в `PLAN.md`).
4. Решения с альтернативами фиксируются в `docs/adr/NNN-название.md` (контекст → варианты → решение → последствия), коротко.
5. Секреты не хранятся в коде. В репозитории только `.env.example`; реальный `.env` генерирует скрипт деплоя.
6. Каждая новая ручка сразу получает: схему Pydantic, описание в Swagger, проверку прав, тест.
7. Язык интерфейса, README и docs: русский. Код и имена: английский.
8. Не удалять никакие файлы без спроса.
