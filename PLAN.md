# План реализации: копия YouTube

Источник: `TZ-YouTube.md`. Документ разбивает работу на модули, которые агент выполняет последовательно. Каждый модуль завершается рабочим состоянием, тестами и коротким отчётом агента.

## 0. Правила работы

Правила работы агента (git только у пользователя, посильность для ИИ, что сознательно не делаем, сквозные правила) вынесены в `AGENTS.md`. Они обязательны для каждого модуля ниже; ссылки «раздел 0.1-0.4» в этом файле указывают на `AGENTS.md`.

## 1. Архитектурные решения (зафиксировать в ADR в M1)


| Область             | Решение                                                                                                                                                                                                                                           | Почему                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Backend             | Python 3.12, FastAPI, SQLAlchemy 2.x (sync) + psycopg 3, Alembic, Pydantic v2                                                                                                                                                                     | требование ТЗ; sync проще для агента и воркера              |
| Слои                | router → service (бизнес-логика и запросы к БД) → модели. Отдельного слоя репозиториев нет                                                                                                                                                        | меньше шаблонного кода                                      |
| БД                  | PostgreSQL 16, расширения `citext`, `pg_trgm`                                                                                                                                                                                                     | требование ТЗ; поиск без внешних движков                    |
| Объектное хранилище | MinIO (S3 API), клиент `boto3`; бакеты приватные, MinIO наружу не опубликован                                                                                                                                                                     | ТЗ проверяет работу с объектным хранилищем                  |
| Загрузка            | Браузер отправляет файл одним `multipart/form-data` запросом на API (XHR, прогресс через `upload.onprogress`). API пишет файл во временный файл на диске и заливает в S3 (`upload_fileobj`)                                                       | проще presigned multipart; не держит файл в памяти          |
| Фоновая обработка   | Контейнер `worker`; очередь заданий в таблице `jobs` PostgreSQL (`SELECT ... FOR UPDATE SKIP LOCKED`)                                                                                                                                             | без Redis, надёжно, легко тестировать                       |
| Транскодирование    | `ffmpeg`: один MP4 (H.264 + AAC, максимум 720p, без апскейла, `+faststart`) и превью JPG                                                                                                                                                          | достаточно для перемотки и воспроизведения в любом браузере |
| Раздача видео       | API проверяет доступ и отдаёт файл из S3 потоком с поддержкой `Range` (206). Для `<video>` и `<img>`, которые не умеют слать заголовок `Authorization`, API выдаёт короткоживущий подписанный токен доступа к конкретному видео в query-параметре | приватные видео не имеют постоянных публичных ссылок        |
| Фронтенд            | Многостраничный: отдельный HTML на экран + общие ES-модули JS и один CSS, без сборки, без внешних CDN; нативный `<video controls>`                                                                                                                | ТЗ: «простой фронт»                                         |
| Прокси              | nginx: статика, `/api` → FastAPI, `/docs`, лимит размера тела, gzip, заголовки безопасности                                                                                                                                                       | единая точка входа                                          |
| Деплой              | Docker Compose + `scripts/deploy.sh` (ставит Docker, генерирует `.env`, поднимает стек, миграции, сидер)                                                                                                                                          | требование «одной командой»                                 |
| Аутентификация      | Access JWT (15 мин, хранится в памяти страницы) + refresh-токен (httpOnly cookie, хэш в БД, ротация); пароли argon2id                                                                                                                             | типовая безопасная схема                                    |
| Роли                | enum `user` / `moderator` / `admin` в `users`; проверка через зависимости FastAPI                                                                                                                                                                 | требование ТЗ                                               |
| Rate limit          | `slowapi`, хранение в памяти процесса; ограничение (счётчики не общие между процессами) описывается в ADR                                                                                                                                         | достаточно для задания                                      |

## M0. Агентная обвязка и каркас проекта

**Цель:** подготовить среду так, чтобы ИИ работал предсказуемо, а проверяющие видели обвязку.

**Задачи**

1. Создать `.gitignore` как обычный файл (Python, `.env`, `__pycache__`, тома данных, временные файлы). Команду `git init` выполняет пользователь.
2. Создать файл CLAUDE.md: цель проекта, стек, структура каталогов, команды (запуск, тесты, линтер, миграции), соглашения по коду, правило «агент не использует git», правило «сначала тест на критичное поведение», правило «после изменений прогонять тесты и линтер», правило «не выходить за рамки раздела 0.3 из `AGENTS.md`», правило формата отчёта по модулю. Положить в файл ссылку на AGENTS.md
3. Создать `.claude/settings.json`: разрешены `pytest`, `ruff`, `alembic`, `docker compose`, `make`, `python`, `curl` к локальному хосту; запрещены все `git`-команды, чтение `.env`, `rm -rf` вне проекта.
4. Подагенты в `.claude/agents/`:
   - `backend-dev` (FastAPI/SQLAlchemy по соглашениям проекта);
   - `frontend-dev` (HTML/CSS/JS без сборки и без внешних CDN);
   - `reviewer` (ревью диффа: безопасность, права доступа, схема БД, соответствие плану).
5. Команды в `.claude/commands/`: `/module <N>` (взять модуль из `PLAN.md`, выполнить, выдать отчёт), `/review` (ревью последних изменений через `reviewer` без git: по списку файлов из отчёта), `/dod` (проверить чек-лист готовности модуля).
6. Один скилл в `.claude/skills/`: `new-endpoint` (шаблон: роутер, схема, сервис, проверка прав, тест).
7. Каталог `prompts/` и `prompts/README.md` (формат промпта: цель, контекст, критерии приёмки).
8. Настроить `ruff` (lint + format, включая правила `S` для безопасности) в `pyproject.toml` и `Makefile` с целями `lint`, `format`, `test`. Без pre-commit.

**Результат:** `CLAUDE.md`, `.claude/**`, `prompts/`, `pyproject.toml`, `Makefile`, `.gitignore`.

**Критерии готовности:** по `CLAUDE.md` агент находит все команды; `make lint` проходит на пустом проекте; в `settings.json` явно запрещён `git`.

## M1. Архитектура, модель данных и ADR

**Цель:** зафиксировать проект системы до написания кода (ТЗ оценивает архитектуру и проектирование БД).

**Задачи**

1. `docs/architecture.md`: диаграмма контейнеров (Mermaid): браузер → nginx → API → PostgreSQL / MinIO; worker → PostgreSQL / MinIO / ffmpeg. Описать слои и два главных потока:
   - загрузка: создать черновик (`uploading`) → отправить файл → проверка и запись в S3 → задание в `jobs`, статус `processing` → worker транскодирует → `ready` или `failed`;
   - просмотр: проверка прав → выдача метаданных и подписанного токена → `GET stream` с `Range` → проксирование из S3.
2. `docs/db.md`: ER-диаграмма (Mermaid) и описание таблиц, индексов, ограничений, политик удаления (см. M3).
3. `docs/security.md` (черновик): матрица прав «гость / пользователь / владелец / модератор / админ × действие».
4. ADR 001-005 (каждый на полстраницы): стек и sync-подход; хранилище и схема загрузки; очередь на PostgreSQL; раздача видео через API с подписанным токеном; аутентификация и rate limit.
5. `docs/acceptance.md`: собственные критерии «работает правильно» (список сценариев приёмки). Они же станут автотестами в M15.

**Результат:** `docs/architecture.md`, `docs/db.md`, `docs/security.md`, `docs/acceptance.md`, `docs/adr/001..005`.

**Критерии готовности:** по документам можно пройти путь от клика до записи в БД и объекта в S3 для загрузки и просмотра.

## M2. Инфраструктурный скелет

**Цель:** весь стек поднимается одной командой, пока с пустым приложением.

**Задачи**

1. `infra/docker-compose.yml`: сервисы `db` (postgres:16, healthcheck, том), `minio` (том) + одноразовый `minio-init` (создаёт приватные бакеты), `api`, `worker`, `nginx`. Наружу публикуется только nginx (порт 80). Порты БД и MinIO не публикуются. Рестарт-политика `unless-stopped`.
2. `backend/Dockerfile`: непривилегированный пользователь; ffmpeg присутствует в образе (общий образ для `api` и `worker`, разные команды запуска); зафиксированные версии зависимостей.
3. `infra/nginx.conf`: раздача `frontend/`, прокси `/api/`, `/docs`, `/openapi.json`, `client_max_body_size` из настройки, увеличенные таймауты для загрузки, `proxy_request_buffering off` для маршрута загрузки, gzip, базовые заголовки безопасности.
4. `.env.example` со всеми переменными (БД, MinIO, JWT-секрет, лимиты загрузки, CORS, роль первого администратора).
5. `backend/app/core/config.py` на `pydantic-settings`; приложение не стартует в `production` с дефолтными секретами.
6. `backend/app/main.py`: приложение, `GET /api/v1/health` (проверка БД и S3), логирование с ID запроса, единый формат ошибок, `/docs`.
7. `Makefile`: `up`, `down`, `logs`, `test`, `lint`, `migrate`, `seed`.

**Критерии готовности:** `make up` поднимает всё; `/api/v1/health` возвращает `ok`; `/docs` открывается через nginx.

## M3. Схема БД и миграции

**Цель:** спроектировать и создать схему данных, как в ER из M1.

**Таблицы**

- `users`: id (UUID), email (`citext`, unique), username (unique), password_hash, role (enum), display_name, avatar_key, is_active, created_at, updated_at.
- `refresh_tokens`: id, user_id, token_hash, expires_at, revoked_at, created_at.
- `channels`: id, owner_id (FK, unique: один канал на пользователя, создаётся при регистрации), handle (unique), name, description, avatar_key, banner_key (необязательно), created_at.
- `videos`: id, channel_id, title, description, status (`uploading` / `processing` / `ready` / `failed`), visibility (`public` / `unlisted` / `private`), source_key, media_key, thumbnail_key, duration_sec, width, height, size_bytes, error_message, views_count, likes_count, dislikes_count, comments_count (денормализованные счётчики), is_hidden, hidden_reason, hidden_by, published_at, created_at, updated_at.
- `video_access`: video_id, user_id (составной PK), granted_at.
- `video_reactions`: user_id, video_id (составной PK), value (`CHECK value IN (-1, 1)`), created_at.
- `comments`: id, video_id, author_id, parent_id (ответ только на комментарий верхнего уровня), body, is_deleted, created_at, updated_at.
- `subscriptions`: subscriber_id, channel_id (составной PK), created_at; `CHECK` запрещает подписку на собственный канал в сервисе (и по возможности в БД).
- `playlists`: id, owner_id, title, description, visibility, created_at.
- `playlist_items`: playlist_id, video_id, position, added_at (уникальность `playlist_id + video_id`).
- `video_views`: id, video_id, user_id (nullable), viewer_hash (хэш IP + User-Agent для гостей), created_at.
- `reports`: id, reporter_id, target_type (`video` / `comment`), target_id, reason (enum), details, status (`open` / `resolved` / `rejected`), resolved_by, resolved_at, created_at.
- `moderation_actions`: id, actor_id, action, target_type, target_id, note, created_at (журнал).
- `jobs`: id, type, payload (JSONB), status (`queued` / `running` / `done` / `failed`), attempts, max_attempts, run_after, locked_at, last_error, created_at.

**Задачи**

1. Модели SQLAlchemy с типами, `CHECK`-ограничениями, внешними ключами и политиками `ON DELETE` (при удалении видео каскадно удаляются реакции, комментарии, доступы, элементы плейлистов).
2. Индексы: `videos(channel_id, created_at DESC)`, `videos(status, visibility, published_at DESC)`, `pg_trgm` GIN на `videos.title` и `channels.name`, `comments(video_id, created_at)`, `subscriptions(channel_id)`, `reports(status, created_at)`, `jobs(status, run_after)`.
3. Alembic: расширения `citext` и `pg_trgm`; миграции применяются командой `make migrate` и автоматически шагом деплоя.
4. Если фактическая схема отличается от плана, обновить `docs/db.md`.
5. Тест: миграции накатываются на пустую БД, откатываются и накатываются повторно.

**Критерии готовности:** `alembic upgrade head` и `alembic downgrade base` проходят; ER в `docs/db.md` соответствует факту.

## M4. Аутентификация и роли

**Задачи**

1. `POST /api/v1/auth/register`: валидация email/username/пароля (минимум 8 символов), создание пользователя и его канала.
2. `POST /api/v1/auth/login`: проверка argon2id; ответ: access JWT (15 мин) в теле и refresh-токен в httpOnly cookie (`SameSite=Lax`, `Secure` при HTTPS).
3. `POST /api/v1/auth/refresh` (ротация: старый токен отзывается, выдаётся новый), `POST /api/v1/auth/logout` (отзыв). Повторное использование отозванного refresh-токена отзывает все токены пользователя.
4. Проверка `Origin` на cookie-эндпоинтах (refresh, logout) как защита от CSRF.
5. `GET/PATCH /api/v1/users/me`, смена пароля (отзывает все refresh-токены), загрузка аватара (проверка типа и размера, хранится в S3, отдаётся через API).
6. Зависимости FastAPI: `get_current_user`, `get_optional_user`, `require_role(...)`; единый формат `401/403`.
7. Rate limit на `login` и `register` (`slowapi`), одинаковое сообщение на «неверный логин или пароль».
8. Админ-ручки: `PATCH /api/v1/admin/users/{id}/role`, `PATCH /api/v1/admin/users/{id}/active` (блокировка). Первый администратор создаётся из переменных окружения при старте/деплое.
9. Тесты: регистрация, дубликаты, вход, неверный пароль, истёкший и подделанный токен, ротация refresh, повторное использование refresh, проверка ролей, заблокированный пользователь не входит.

**Критерии готовности:** сценарии аутентификации покрыты тестами; в БД только argon2-хэши; токены и пароли не попадают в логи.

## M5. Хранилище и загрузка видео

**Цель:** надёжно принять файл и положить его в объектное хранилище.

**Задачи**

1. `app/storage/`: интерфейс `ObjectStorage` (`put`, `get`, `get_range`, `head`, `delete`, `delete_prefix`) и реализация на `boto3` для MinIO; in-memory реализация для тестов.
2. Бакеты (все приватные): `videos` (ключи `source/{video_id}.{ext}`, `media/{video_id}.mp4`), `thumbnails`, `avatars`. Ключи генерирует сервер, имя файла пользователя в ключ не попадает.
3. Эндпоинты:
   - `POST /api/v1/videos`: создать черновик (`title`, `description`, `visibility`), статус `uploading`;
   - `POST /api/v1/videos/{id}/upload`: принять файл `multipart/form-data`, записать во временный файл, проверить, залить в S3, статус `processing`, создать задание в `jobs`. Повторный вызов для видео не в статусе `uploading` возвращает 409;
   - `DELETE /api/v1/videos/{id}` отменяет и удаляет (используется и для отмены загрузки).
4. Валидация: белый список расширений и MIME (mp4, mov, mkv, webm, avi), проверка сигнатуры файла (magic bytes), лимит размера (по умолчанию 500 МБ, из env, считается на сервере по факту), лимит числа незавершённых загрузок на пользователя.
5. Только владелец канала может загружать файл в своё видео.
6. Периодическая очистка (в цикле воркера): видео в статусе `uploading` старше 24 часов удаляются вместе с объектами.
7. Тесты: успешная загрузка, неверный тип, превышение размера, чужое видео (403), повторная загрузка (409), удаление очищает S3.

**Критерии готовности:** файл 100+ МБ загружается без роста памяти API (проверить по памяти контейнера); объект лежит в MinIO.

## M6. Фоновая обработка видео (worker)

**Цель:** превратить исходник в воспроизводимый MP4 и превью.

**Задачи**

1. Очередь: воркер забирает задание `FOR UPDATE SKIP LOCKED`, ставит `running`; при ошибке увеличивает `attempts`, откладывает `run_after` (экспоненциальная задержка); после `max_attempts` — `failed`. Задания `running` с устаревшим `locked_at` возвращаются в очередь.
2. Пайплайн `process_video(video_id)`:
   - скачать исходник во временный каталог;
   - `ffprobe`: длительность, разрешение, наличие видеопотока; отказ при некорректном файле или превышении лимита длительности (настраивается);
   - `ffmpeg`: MP4 (H.264 + AAC), масштабирование до 720p без апскейла, `-movflags +faststart`;
   - превью: один кадр JPG примерно с 10% длительности;
   - загрузить результаты в S3, записать `media_key`, `thumbnail_key`, `duration_sec`, `width`, `height`, `size_bytes`;
   - `status=ready`, `published_at=now()`; исходник удалить (флаг в настройках); временные файлы очистить;
   - при окончательной ошибке: `status=failed`, `error_message` с понятным текстом.
3. Безопасность ffmpeg: запуск через `subprocess` со списком аргументов (без shell), таймаут, лимит ресурсов контейнера.
4. `GET /api/v1/videos/{id}/processing`: статус и сообщение для UI (владельцу).
5. Тесты: короткий ролик создаётся фикстурой через `ffmpeg -f lavfi`; успешная обработка; битый файл → `failed`; два воркера не берут одно задание.

**Критерии готовности:** после загрузки видео само переходит в `ready`; в S3 есть MP4 и превью; ошибка обработки отражается статусом `failed`.

## M7. Просмотр видео: метаданные, приватность, раздача

**Цель:** лента, страница видео, приватные видео, безопасный стриминг.

**Задачи**

1. Видимость: `public` (лента и поиск), `unlisted` (только по ссылке), `private` (владелец, администратор, модератор и пользователи из `video_access`).
2. Единая функция `can_view(user, video)`: учитывает владельца, роль, `video_access`, статус и `is_hidden`. Используется во ВСЕХ ручках, отдающих метаданные, поток, превью, комментарии, реакции.
3. Ручки:
   - `GET /api/v1/videos`: лента (публичные `ready`, не скрытые, пагинация `limit/offset` или по курсору, сортировка: новые / популярные);
   - `GET /api/v1/videos/{id}`: метаданные, канал, счётчики, реакция текущего пользователя, признак подписки, `stream_url` и `thumbnail_url` (для не публичных видео с подписанным токеном);
   - `PATCH /api/v1/videos/{id}`: правка названия, описания, видимости (владелец);
   - `GET /api/v1/me/videos`: мои видео со статусами (для студии);
   - `GET /api/v1/videos/{id}/related`: до 12 видео того же канала и самые просматриваемые публичные (без рекомендательных алгоритмов).
4. Приватный доступ: `GET/PUT/DELETE /api/v1/videos/{id}/access` (добавление по username или email), только владелец.
5. Раздача:
   - `GET /api/v1/videos/{id}/stream`: проверка доступа, `HEAD` к S3, поддержка `Range` (206, `Content-Range`, `Accept-Ranges`), потоковая передача чанками;
   - `GET /api/v1/videos/{id}/thumbnail`;
   - подписанный токен: короткоживущий JWT (5-10 минут) со ссылкой на конкретное видео, принимается в `?token=` на `stream` и `thumbnail`; токен от одного видео не работает для другого;
   - `Cache-Control: private` для не публичных видео.
6. Просмотры: `POST /api/v1/videos/{id}/view` засчитывает не чаще одного раза за 30 минут на пользователя или `viewer_hash`; счётчик обновляется атомарным `UPDATE ... SET views_count = views_count + 1`.
7. Скрытое модератором видео: владельцу и модераторам доступно с пометкой, остальным 404.
8. Тесты (критично): матрица доступа «гость / чужой / владелец / получивший доступ / модератор × public / unlisted / private / hidden × метаданные / поток / превью»; подписанный токен чужого видео и просроченный отклоняются; прямого доступа к S3 снаружи нет.

**Критерии готовности:** загруженное видео воспроизводится по `stream` с перемоткой (`Range`); приватное недоступно посторонним по всем путям; матрица доступа покрыта тестами.

## M8. Лайки, комментарии, подписки

**Задачи**

1. Реакции: `PUT /api/v1/videos/{id}/reaction` (`value` = 1 или -1; смена реакции допустима), `DELETE` снимает. Счётчики обновляются в той же транзакции; реагировать на недоступное видео нельзя.
2. Комментарии: `GET /api/v1/videos/{id}/comments` (пагинация, сортировка «новые сверху», ответы в один уровень вложенности), `POST` (длина до 2000 символов), `PATCH` (автор), `DELETE` (автор, владелец видео, модератор; soft delete с текстом «комментарий удалён»), счётчик `comments_count`.
3. Подписки: `PUT/DELETE /api/v1/channels/{id}/subscription`, `GET /api/v1/me/subscriptions`, `GET /api/v1/feed/subscriptions` (новые видео подписанных каналов). Нельзя подписаться на себя. Число подписчиков считается запросом (`COUNT`) или отдельным счётчиком.
4. Rate limit на комментарии и реакции.
5. Тесты: повторный лайк идемпотентен, лайк → дизлайк меняет оба счётчика корректно, права на удаление комментария, ответ на ответ отклоняется, подписка/отписка, лента подписок.

**Критерии готовности:** сценарий «регистрация → вход → создание видео → загрузка → готово → просмотр → лайк → комментарий» проходит как интеграционный тест через API (первая версия e2e).

## M9. Каналы и плейлисты

**Задачи**

1. `GET /api/v1/channels/{handle}`: профиль (название, описание, аватар, число подписчиков, подписан ли текущий пользователь); `PATCH` (владелец); загрузка аватара (баннер необязателен).
2. `GET /api/v1/channels/{handle}/videos`: публичные для всех; владельцу также `private`/`unlisted` и видео в обработке; сортировка «новые / популярные».
3. Плейлисты: `POST/GET/PATCH/DELETE /api/v1/playlists`, `PUT/DELETE /api/v1/playlists/{id}/items/{video_id}` (новый элемент добавляется в конец), `GET /api/v1/channels/{handle}/playlists`. Перестановка элементов необязательна. В выдаче плейлиста видео, недоступные текущему пользователю, не показываются.
4. Тесты: видимость видео на канале; приватное видео не просачивается через плейлист; чужой плейлист изменить нельзя.

**Критерии готовности:** страница канала получает данные одним-двумя запросами; приватное не видно в публичных списках.

## M10. Поиск

**Задачи**

1. `GET /api/v1/search?q=&type=video|channel&sort=relevance|date|views&limit=&offset=`.
2. Реализация: `ILIKE '%q%'` по названию (описание вторично) с триграммным индексом и сортировкой по `similarity()` и дате; для каналов по `name` и `handle`. Без `tsvector`, без морфологии.
3. В результаты попадают только видео, доступные гостю (`public`, `ready`, не скрытые).
4. Валидация: длина запроса от 1 до 100 символов, экранирование `%` и `_`, ограничение выдачи.
5. Тесты: точное и частичное совпадение, регистр, русский и английский текст, скрытое и приватное не находится, спецсимволы не ломают запрос.

**Критерии готовности:** поиск находит видео по части названия и не раскрывает закрытые видео.

## M11. Модерация и администрирование

**Задачи**

1. Жалобы: `POST /api/v1/reports` (видео или комментарий, причина из списка + текст). Одна открытая жалоба от пользователя на объект. Rate limit.
2. Очередь модерации (роли `moderator`, `admin`): `GET /api/v1/moderation/reports` (фильтры по статусу и типу, пагинация), `GET /api/v1/moderation/reports/{id}` с данными объекта.
3. Действия: скрыть и вернуть видео (`is_hidden`, `hidden_reason`), удалить комментарий, закрыть жалобу (`resolved` / `rejected`) с заметкой. Каждое действие записывается в `moderation_actions`; `GET /api/v1/moderation/actions` показывает журнал.

5. Администратор: назначение и снятие роли модератора, блокировка и разблокировка пользователей (заблокированный не входит, его видео скрыты из публичных списков). Модератор не может менять роли и блокировать администраторов; последнего администратора разжаловать нельзя.
6. Тесты: обычный пользователь получает 403; скрытое модератором видео пропадает из ленты и поиска, остаётся у владельца с пометкой; журнал заполняется; ограничения ролей работают.

**Критерии готовности:** цикл «жалоба → решение модератора → видео скрыто или возвращено» работает и попадает в журнал.

## M13. Фронтенд: экраны

Каждый экран делается вместе с подключением к реальному API и ручной проверкой в браузере.

1. **Вход и регистрация:** формы, валидация на клиенте, ошибки сервера, переход после входа, выход.
2. **Главная:** сетка карточек, чипы «Все / Новые / Популярные», подгрузка при прокрутке.
3. **Просмотр видео:** `<video controls>` с `stream_url`, название и описание (разворачиваемое), канал с кнопкой «Подписаться», лайк и дизлайк, «Поделиться» (копирование ссылки), «Пожаловаться» (модальное окно), комментарии (список, добавление, ответ, удаление своего), колонка «Похожие» справа, плашки статусов `processing` / `failed` для владельца, страницы 403 и 404.
4. **Канал:** шапка (аватар, название, `@handle`, число подписчиков, кнопка «Подписаться»), вкладки «Видео» / «Плейлисты» / «О канале», сортировка, кнопки редактирования для владельца.
5. **Поиск:** строка поиска в шапке, страница результатов (видео и каналы), подгрузка.
6. **Загрузка:** выбор файла (кнопка и drag-and-drop), проверка расширения и размера на клиенте, файл начинает загружаться сразу, прогресс-бар (проценты, МБ, отмена), параллельно форма метаданных (название, описание, видимость), кнопка «Опубликовать», после загрузки показывается статус обработки (опрос `processing` раз в 2-3 секунды) и ссылка на видео.
7. **Студия «Мои видео»:** таблица видео со статусами и видимостью, правка метаданных, управление доступом к приватным видео (добавить и убрать пользователя), удаление с подтверждением, пометка скрытых модератором.
8. **Модерация:** очередь жалоб с фильтрами, просмотр объекта, кнопки «Скрыть видео», «Вернуть видео», «Удалить комментарий», «Отклонить жалобу», вкладка журнала; для администратора управление ролями и блокировками. Страница доступна только нужным ролям (проверка и на клиенте, и на сервере).
9. **Плейлисты:** создание, добавление видео через меню «Сохранить» на странице видео, страница плейлиста со списком.
10. Для всех экранов: состояния загрузки, ошибки и пустого списка; `alt` у изображений; фокус и `aria-label` у кнопок-иконок; проверка на узком экране.

**Критерии готовности:** сценарий «регистрация → загрузка → просмотр → лайк и комментарий» проходит целиком через UI без ручных запросов.

## M14. Безопасность: аудит и усиление

**Задачи**

1. Ревью через подагента `reviewer` по чек-листу:
   - авторизация на каждой ручке, IDOR (чужие видео, комментарии, плейлисты, студия);
   - Pydantic-схемы без лишних полей (массовое присваивание);
   - только параметризованные запросы;
   - XSS (комментарии, названия, описания, имена);
   - CSRF на cookie-эндпоинтах;
   - ключи S3 генерирует сервер (нет path traversal);
   - в API нет запросов по URL, заданным пользователем (SSRF).
2. Загрузка файлов: белый список, magic bytes, `ffprobe`, лимиты, загруженные файлы нигде не исполняются.
3. Заголовки (nginx): `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`. `HSTS` добавляется только при HTTPS.
4. HTTPS: по умолчанию HTTP на порту 80 (проверочная VM без домена). В `docs/deploy.md` описать, как поставить TLS перед nginx (Caddy или certbot). Автоматизации сертификатов в деплое нет.
5. Секреты: деплой генерирует случайные `JWT_SECRET` и пароли БД и MinIO; приложение в `production` отказывается стартовать с дефолтами.
6. Rate limit: вход, регистрация, комментарии, жалобы, загрузка.
7. Контейнеры: непривилегированные пользователи, порты БД и MinIO не опубликованы.
8. Запуск `bandit` и `pip-audit`, исправление критичных находок; `ruff` с правилами `S`.
9. Логи без паролей, токенов и полных адресов email; журнал аудита (вход, смена роли, модерация).
10. Негативные тесты в `tests/security/`: IDOR, обход ролей, подделанный и просроченный JWT, подписанный токен чужого видео, XSS-пейлоады в комментарии и названии (проверка, что API хранит строкой, а фронт выводит через `textContent`), слишком большое тело, неверный тип файла.
11. Итоговый `docs/security.md`: модель угроз (кратко), матрица прав, принятые меры, известные ограничения (rate limit в памяти процесса, HTTP по умолчанию).

**Критерии готовности:** тесты безопасности зелёные; `bandit` и `pip-audit` без критичных находок; чек-лист ревью пройден.

1. `README.md`: что это, быстрый старт (команда деплоя), демо-учётные данные, адреса (`/`, `/docs`), структура репозитория, команды `make`, запуск тестов, переменные окружения, честный список того, что не реализовано (раздел 0.3 из `AGENTS.md`).
2. Актуализировать `docs/architecture.md` и `docs/db.md` по факту, дополнить `docs/deploy.md`, `docs/security.md`, `docs/testing.md`.
3. `docs/ai-workflow.md`: как использовался ИИ (декомпозиция на модули, подагенты, команды, скилл, как проверялись результаты, что правилось вручную и почему).
4. Swagger: теги, описания, коды ответов, схема безопасности Bearer.
5. `docs/acceptance.md`: таблица «критерий → как проверено → тест».

**Критерии готовности:** человек без контекста по README разворачивает и проверяет систему за 15 минут.

## M19. Финальная проверка и подготовка к сдаче

**Задачи агента (без git)**

1. Полный прогон на чистой Ubuntu: одна команда деплоя → `smoke.sh` → сценарий в UI → `make test`.
2. Сверка с критериями проверки из ТЗ: объём, соответствие оригиналу (по экранам), разворачиваемость, архитектура, БД, ИИ и обвязка, безопасность.
3. Поиск секретов в файлах рабочего каталога (шаблоны ключей, пароли, `.env` не должен лежать в проекте).
4. Подготовить `docs/submission-checklist.md` для пользователя (см. ниже).

**Задачи пользователя (агент их не выполняет)**

1. Привести историю коммитов в порядок, не переписывая и не склеивая её; убедиться, что `git status` чист и в истории нет секретов.
2. Скопировать диалоги из `~/.claude/projects/<проект>/*.jsonl` целиком, без правок и пересказов, в архив (например, `ai-dialogs/claude-code/`).
3. Убедиться, что в архиве лежит вся обвязка как есть: `CLAUDE.md`, `.claude/` (agents, skills, commands, settings.json), `.mcp.json` (если есть), `prompts/`.
4. Собрать zip вместе с каталогом `.git`, распаковать в чистый каталог и проверить содержимое.

**Критерии готовности:** чек-лист для пользователя готов; архив, собранный по нему, соответствует разделу «Что сдать» из ТЗ.

## Порядок выполнения и зависимости

```
M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8   (вертикальный срез через API)
                                 M12 можно начинать параллельно с M7
M8 → M9 → M10 → M11
M12 → M13 (экраны по мере готовности API)
M14 — после M11 и M13 (но проверки безопасности закладываются с M4)
M15 — тесты пишутся с каждым модулем, M15 собирает и дополняет
M16 — после M11, до M17
M17 → M18 → M19
```

Ориентир по времени (10 дней): M0-M2 — день 1; M3-M4 — день 2; M5-M7 — дни 3-4; M8-M11 — дни 5-6; M12-M13 — дни 6-8 (параллельно с бэкендом); M14-M16 — день 9; M17-M19 — день 10.

При нехватке времени сначала сокращаем: плейлисты (M9), баннеры, подсказки поиска, журнал модерации в UI, `backup.sh`. Не сокращаем: вертикальный срез, приватность видео, тесты критичного поведения, деплой одной командой, документацию, обвязку.

Опциональные расширения (только после M19 и по решению пользователя): HLS с несколькими качествами, возобновляемая загрузка по чанкам, тёмная тема, подсказки поиска, лайки комментариев.
